How to read this report

  • Amazon EFS is a network file system. This report compares two clients for it: nfs-crust and the Linux NFS client.
  • KiB and MiB are binary data sizes: 1 KiB is 1,024 bytes and 1 MiB is 1,024 KiB. ops/s means completed operations per second; MiB/s means payload data completed per second.
  • µs means microseconds, or millionths of a second. ms means milliseconds, or thousandths of a second. CPU-ms/op is the processor time used for each completed operation.
  • p50 is the median or typical response time: half of operations completed faster and half slower. p99 is the slowest-1% threshold: 99 of every 100 operations completed at or below it. p99.9 is the equivalent threshold for 999 of every 1,000 operations.
  • Concurrent workers repeatedly start an operation and wait for it to finish before starting the next. More workers allow more operations to be in progress at once.
  • Scheduled-load tests start operations at a fixed target rate even when earlier operations are still unfinished. This exposes waiting and queue buildup that the worker tests can hide.
  • 85% means 85% of a client's measured peak request rate. It does not mean processor use, EFS I/O use, or any other resource-utilization percentage.
  • For response time and processor cost, lower is better. For throughput, higher is better.

Throughput as concurrent work increases

These tests use 1, 8, or 32 workers. Each worker starts its next operation only after its previous operation finishes. Throughput is the median across repeated runs and counts payload bytes completed through the end of the operation, not bytes sent over the network.

Response time under scheduled load

These tests schedule 128 KiB known-size reads and create-new writes at a fixed rate, whether or not earlier operations have finished. Response time begins at the scheduled start time, so it includes time waiting for its turn to run as well as time doing the operation.

Same request rate gives both clients 85% of the slower client's measured peak request rate. Each client at its own rate gives each client 85% of its own measured peak. These percentages describe scheduled request rates—not processor use or EFS utilization.

The benchmark uses the demanding 85% load level. Client order was reversed across runs to reduce order bias.

Sample-size check: 83 of 144 runs have fewer than 1,000 successful operations for p99; 140 have fewer than 10,000 for p99.9. Those minimums provide about ten operations beyond each threshold. They do not, by themselves, guarantee statistical confidence.

Data quality and correctness

  • Host-wide TCP counters recorded 52 retransmitted segments and 0 established resets during the run.
  • 144 runs across 72 configurations produced 287,469 successful operation samples. 0 create-new outcomes required a follow-up check after the final server reply was lost or inconclusive.
  • Data-content checks run outside the timed operation. The benchmark verifies replaced files, a sample of newly created files, and deleted files by reading them through the other client.
  • An error during untimed preparation, or a measurement with no successful operations, invalidates that test configuration. A follow-up check that is mismatched or inconclusive remains an error.
  • Downloaded-file integrity: all 23 downloaded-file checksums verified. Raw success/error counts, follow-up-check flags, and response-time data agree with each run's summary.

Method

  • The test created a fresh, encrypted Regional EFS file system using General Purpose performance mode and Elastic throughput. Its network endpoint was in the same subnet and Availability Zone as the EC2 test machine.
  • Both clients connected to the same private EFS address from one dedicated c7g.xlarge. Timed operations did not pass through the developer workstation or AWS Systems Manager.
  • Both clients used NFSv4.1 over TLS encryption with traditional Unix user/group credentials. nfs-crust verified the EFS server's DNS name against public certificate authorities; Linux used Amazon's EFS mount helper. EFS identity-based (IAM) authorization was off.
  • nfs-crust requested up to 64 in-flight NFS requests per connection, split reads into 1 MiB chunks, and split writes into 504 KiB EFS-compatible chunks. Individual tests requested 128 KiB or 1 MiB at a time.
  • Linux reads used o-direct mode to bypass the file-data memory cache. Linux file-metadata and directory operations used its normal mounted-file-system path. Results explicitly labeled as memory-cache context are never presented as comparable remote EFS reads.
  • Results apply to this EC2 type, EFS configuration, region and Availability Zone, Linux kernel, and measurement window. Each configuration has 2 separate runs. The uncertainty intervals describe variation among those runs; they do not capture other machines, times, regions, or production environments.
  • Read tests rotate among two files per worker. Linux bypassed its memory cache, but both clients still read files that had already been accessed. These are not first-read or production-traffic measurements.
